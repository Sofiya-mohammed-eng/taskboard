# Incident: v0.1.1 frontend could not reach the API

**Date:** 2026-09-29
**Severity:** High — the app was unusable through the browser
**Status:** Resolved in v0.1.2

## Summary

Release `v0.1.1` shipped with the frontend's Nginx proxy pointed at the
wrong port (`9000` instead of the API's real port, `8000`). The API
container itself was healthy, but every request routed through the
frontend failed with `502 Bad Gateway`. CI passed on the change because
neither the `test` job nor the `build` job exercises the frontend proxy
path: `test` talks to the API directly, and `build` only confirms the
images build, not that they work together.

## Timeline

- Bug introduced: a one-line change to `frontend/nginx.conf`,
  `proxy_pass http://api:9000/` instead of `http://api:8000/`.
- CI (`test`, `build`) passed on the pull request; the change was
  squash-merged to `main`.
- Tagged and released as `v0.1.1`. The release workflow built and
  published the broken image, exactly as CI had approved it.
- Deployed `v0.1.1` with `docker-compose.release.yml` and reproduced the
  failure:
  - `GET /health` direct to the API: `200 OK`
  - `GET /api/tasks` through the frontend proxy: `502 Bad Gateway`
  - The browser loaded the page, but the task list stayed empty and
    adding a task failed with "Could not add task."
- Rolled back to `v0.1.0` per the runbook
  (`TAG=v0.1.0 docker compose -f docker-compose.release.yml up -d`).
  Verified `/api/tasks` returned real data and a new task could be added.
- Fixed the port in `frontend/nginx.conf`, opened a pull request,
  waited for `test` and `build` to pass, and squash-merged it.
- Tagged and released `v0.1.2`. Deployed it and confirmed `/api/tasks`
  returned data and a new task could be added and read back.

## Root cause

A typo in `frontend/nginx.conf`'s `proxy_pass` directive. Nothing in
the pipeline runs the three containers together and calls the app the
way a real user would, so a config-only bug like this has no test
covering it.

## Detection

Manual verification after deployment: a direct health check against
the API succeeded while the same request through the frontend's proxy
returned `502`. The gap between "the backend is healthy" and "the app
works" is what made this bug possible, and is exactly what needs to be
covered going forward.

## Resolution

Corrected the port in `frontend/nginx.conf`, verified through the same
manual check, and released `v0.1.2`.

## Follow-up

- Add an end-to-end check to CI that starts all three containers with
  the release compose file and confirms the frontend can reach the API
  through the proxy, not just that each image builds. This is the gap
  that let the bug through, and it is the single highest-value fix from
  this incident.
- Add a smoke test to the release workflow itself: after publishing
  images, deploy them and hit `/api/tasks` through the proxy before
  considering the release successful.
